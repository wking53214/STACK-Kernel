# P3.2: Hard Preemption Schema Design

**Author**: William N. King (with Claude Haiku 4.5)  
**Date**: 2026-10-01  
**Status**: Schema Design Phase (Implementation to follow)

---

## Purpose

Design a relational schema that captures execution context and trap events for the P3.2 hybrid boundary model. The schema must support:

1. **Live queries**: Real-time boundary decisions (should this preemption be enforced right now?)
2. **Historical analysis**: Pattern discovery for boundary reorganization (which boundaries trap most, why, in what states?)
3. **Flywheel mechanism**: Trap events inform Sentinel, which proposes tighter boundaries for next execution

---

## Hybrid Boundary Model (P3.2)

Signal handler sets preemption flag; does not attempt unwinding (signal-safe).

Preemption state travels with execution context (context-local, not broadcast flag mesh).

Boundaries are active observers: when preemption catches, boundary logs what was executing, where, and why it trapped.

Trap events become Sentinel input for governance learning.

## Schema Structure

### Table 1: `execution_contexts`

**Purpose**: Track the execution state at any moment a trap event occurs.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `context_id` | uuid | PRIMARY KEY | Unique identifier for this execution context |
| `transaction_id` | uuid | FOREIGN KEY → transactions | Which transaction this context belongs to |
| `agent_id` | text | NOT NULL | Which agent/payload is running (CNS subject binding) |
| `subject_digest` | bytea | NOT NULL | SHA-256 of agent code/identity (immutable) |
| `depth` | integer | NOT NULL, >= 0 | Call stack depth at trap time |
| `boundary_layer` | integer | NOT NULL, 1-6 | Which layer (1=clock, 2=preemption, etc.) |
| `issued_at_unix_ns` | bigint | NOT NULL | Nanosecond timestamp (when context entered) |
| `wall_clock_at_entry` | bigint | NOT NULL | OS wall-clock time at entry (for correlation) |
| `hardware_ticks_at_entry` | bigint | NOT NULL | Hardware clock ticks at entry (Layer 1) |
| `preemption_flag_at_entry` | boolean | NOT NULL | Was preemption already active? |
| `deadline_ns` | bigint | NOT NULL | Deadline for this transaction (from Layer 2) |
| `tokens_consumed` | bigint | NOT NULL, >= 0 | Rate-limit tokens consumed so far (Layer 3) |
| `tokens_capacity` | bigint | NOT NULL, > 0 | Rate-limit capacity (configured) |
| `capabilities_mask` | bytea | NOT NULL | Active capability mask at entry (Layer 4) |
| `memory_allocated_bytes` | bigint | NOT NULL, >= 0 | Bytes allocated from arena at entry (Layer 6) |
| `memory_capacity_bytes` | bigint | NOT NULL, > 0 | Arena capacity (configured) |
| `created_at` | timestamp | DEFAULT NOW() | When this record was inserted |

**Indexes**:
- `(transaction_id, boundary_layer)` - for live queries
- `(agent_id, issued_at_unix_ns)` - for agent history
- `(issued_at_unix_ns DESC)` - for time-range scans
- `(subject_digest)` - for payload-based analysis

**Purpose**: Every time a boundary is checked, a context is created. This captures the full execution state, enabling Sentinel to ask: "What state was the payload in when this boundary triggered?"

---

### Table 2: `trap_events`

**Purpose**: Record when a boundary refused or halted a payload.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `trap_id` | uuid | PRIMARY KEY | Unique identifier for this trap |
| `context_id` | uuid | NOT NULL, FOREIGN KEY | Execution context when trap occurred |
| `transaction_id` | uuid | NOT NULL, FOREIGN KEY | Which transaction |
| `agent_id` | text | NOT NULL | Which agent triggered the trap |
| `subject_digest` | bytea | NOT NULL | Payload identity (for correlation) |
| `boundary_layer` | integer | NOT NULL, 1-6 | Which layer detected the trap |
| `trap_reason` | text | NOT NULL | Why was it trapped? (enum: deadline_exceeded, token_exhausted, capability_denied, memory_exceeded, signal_delivered, etc.) |
| `trap_outcome` | text | NOT NULL | CNS outcome: RETRY, TERMINAL_BREACH, or HALT |
| `preemption_active_at_trap` | boolean | NOT NULL | Was preemption flag set when this was caught? |
| `hardware_ticks_at_trap` | bigint | NOT NULL | Hardware ticks when trap was recorded |
| `nanoseconds_since_deadline` | bigint | NULL | How far past deadline (or NULL if not deadline trap) |
| `tokens_deficit` | bigint | NULL | How far over quota (or NULL if not rate-limit trap) |
| `capability_mask_denied` | bytea | NULL | Which capability was denied (or NULL) |
| `memory_requested_bytes` | bigint | NULL | How much memory was requested (or NULL) |
| `retry_after_ns` | bigint | NULL | If RETRY, when should retry (absolute Unix ns) |
| `created_at` | timestamp | DEFAULT NOW() | When trap was recorded |

**Indexes**:
- `(transaction_id)` - for transaction history
- `(agent_id, boundary_layer)` - for agent-layer patterns
- `(boundary_layer, trap_reason)` - for layer-reason patterns
- `(created_at DESC)` - for recent traps
- `(subject_digest, trap_reason)` - for payload-specific patterns

**Purpose**: Every time a boundary enforces a rule (deadline, quota, capability, memory), a trap is recorded. This is the primary input to Sentinel's pattern analysis.

---

### Table 3: `transactions`

**Purpose**: Group execution contexts and traps into logical units.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `transaction_id` | uuid | PRIMARY KEY | Unique identifier |
| `agent_id` | text | NOT NULL | Which agent initiated this transaction |
| `subject_digest` | bytea | NOT NULL | Payload identity |
| `started_at_ns` | bigint | NOT NULL | Transaction start time (Unix ns) |
| `deadline_ns` | bigint | NOT NULL | When transaction must complete |
| `outcome` | text | NOT NULL | Final outcome: PASS, RETRY, TERMINAL_BREACH, HALTED |
| `completed_at_ns` | bigint | NULL | When transaction finished (or NULL if halted) |
| `execution_ns` | bigint | NULL | Actual execution duration (NULL if halted) |
| `trap_count` | integer | NOT NULL, >= 0 | How many boundaries trapped during execution |
| `created_at` | timestamp | DEFAULT NOW() | When transaction record was inserted |

**Indexes**:
- `(agent_id, started_at_ns DESC)` - for agent timeline
- `(outcome, completed_at_ns)` - for outcome analysis
- `(deadline_ns)` - for deadline misses

**Purpose**: Transactions are the top-level unit. Each transaction has zero or more contexts (one per boundary check) and zero or more traps (when boundaries enforce).

## Query Patterns

### Live Queries: Boundary Decisions

**Q1: Should preemption halt this transaction right now?**

```sql
SELECT 
    t.deadline_ns,
    t.started_at_ns,
    ec.hardware_ticks_at_entry,
    ec.preemption_flag_at_entry
FROM transactions t
JOIN execution_contexts ec ON t.transaction_id = ec.transaction_id
WHERE t.transaction_id = $1
  AND t.outcome IS NULL  -- Still running
  AND ec.boundary_layer = 2  -- Preemption layer
ORDER BY ec.issued_at_unix_ns DESC
LIMIT 1;
```

**Use**: Layer 2 boundary checks this before deciding whether to unwind.

---

**Q2: Can this agent acquire more tokens right now?**

```sql
SELECT 
    ec.tokens_consumed,
    ec.tokens_capacity,
    t.started_at_ns
FROM execution_contexts ec
JOIN transactions t ON ec.transaction_id = t.transaction_id
WHERE ec.agent_id = $1
  AND t.outcome IS NULL  -- Still running
  AND ec.boundary_layer = 3  -- Rate-limit layer
ORDER BY ec.issued_at_unix_ns DESC
LIMIT 1;
```

**Use**: Layer 3 rate limiter decides if admission is possible.

---

### Historical Queries: Pattern Discovery

**Q3: Which boundaries trap which agents most?**

```sql
SELECT 
    agent_id,
    boundary_layer,
    trap_reason,
    COUNT(*) as trap_count,
    AVG(CASE 
        WHEN trap_reason = 'deadline_exceeded' THEN nanoseconds_since_deadline
        ELSE 0 
    END) as avg_deadline_overage_ns
FROM trap_events
WHERE created_at > NOW() - INTERVAL '1 hour'
GROUP BY agent_id, boundary_layer, trap_reason
ORDER BY trap_count DESC
LIMIT 20;
```

**Use**: Sentinel identifies which agents consistently miss which boundaries.

---

**Q4: What is the pattern of traps for a single agent across all boundaries?**

```sql
SELECT 
    boundary_layer,
    trap_reason,
    COUNT(*) as count,
    MIN(created_at) as first_trap,
    MAX(created_at) as last_trap
FROM trap_events
WHERE agent_id = $1
  AND created_at > NOW() - INTERVAL '24 hours'
GROUP BY boundary_layer, trap_reason
ORDER BY boundary_layer, count DESC;
```

**Use**: Sentinel analyzes a specific agent's trap history to propose boundary changes.

---

**Q5: Are certain capability denials clustering around specific agents or times?**

```sql
SELECT 
    agent_id,
    capability_mask_denied,
    COUNT(*) as denial_count,
    MAX(created_at) as latest_denial
FROM trap_events
WHERE trap_reason = 'capability_denied'
  AND created_at > NOW() - INTERVAL '1 day'
GROUP BY agent_id, capability_mask_denied
HAVING COUNT(*) > 5
ORDER BY denial_count DESC;
```

**Use**: Sentinel proposes tighter capability masks for agents with repeated denials.

---

**Q6: Memory pressure analysis: Are certain agents hitting memory limits?**

```sql
SELECT 
    agent_id,
    memory_capacity_bytes,
    COUNT(*) as memory_trap_count,
    AVG(memory_requested_bytes) as avg_request_bytes,
    MAX(memory_requested_bytes) as max_request_bytes
FROM trap_events
WHERE trap_reason = 'memory_exceeded'
  AND created_at > NOW() - INTERVAL '1 day'
GROUP BY agent_id, memory_capacity_bytes
ORDER BY memory_trap_count DESC;
```

**Use**: Sentinel proposes arena capacity increases or agent-specific limits.

## Flywheel Mechanism

1. **Agent executes** → contexts and traps recorded in real time
2. **Sentinel queries** (Q3-Q6) run hourly to identify patterns
3. **Sentinel analysis** identifies which boundaries catch most traps, which agents are chronic offenders
4. **Boundary reorganization** (proposed by Sentinel):
   - Tighten deadline windows for agents that miss frequently
   - Reduce rate-limit tokens for quota-busters
   - Revoke capabilities for agents that trigger denials
   - Reorganize arena allocation strategy
5. **Next transaction** loads reorganized boundaries
6. **New traps inform next round** of analysis

## Implementation Considerations

### Data Volume

At 1,000 transactions/second with average 10 traps per transaction:
- `execution_contexts`: ~10,000 rows/second
- `trap_events`: ~10,000 rows/second
- Monthly retention: ~26 billion rows

**Partitioning strategy**: Partition by `created_at` (daily or hourly) for efficient archival.

---

### Consistency Model

- **execution_contexts**: Inserted before trap_events that reference them
- **trap_events**: Inserted synchronously when boundary evaluates (must not block transaction)
- **transactions**: Marked complete when transaction finishes (may lag slightly)

**Isolation**: Use `INSERT ... ON CONFLICT` for idempotent trap recording (same trap recorded twice = duplicate entry, not error).

---

### Indexing for Latency

Live queries (Q1, Q2) run inside critical section; must complete in <1ms:
- `(transaction_id, boundary_layer)` with partial index for `outcome IS NULL`
- `(agent_id, issued_at_unix_ns DESC)` partial index for live transactions only

Historical queries can afford higher latency (Sentinel analysis runs offline).

---

### Retention Policy

- **Live queries**: Indexes on `outcome IS NULL` (transactions in flight)
- **Recent history**: Keep 24 hours of all traps (for pattern discovery)
- **Archive**: Compress and move older traps to cold storage (after Sentinel analysis completes)

## Schema Validation

Before deploying P3.2, verify:

1. ✓ CNS subject binding: Every trap record includes `subject_digest` (immutable, unforgeable)
2. ✓ Causality: `execution_contexts` → `trap_events` → `transactions` links are consistent
3. ✓ Completeness: No boundary check occurs without an `execution_context` record
4. ✓ Liveness: Live queries execute in <1ms on indexed columns
5. ✓ Auditability: Every trap is queryable by agent, boundary, time, and reason
